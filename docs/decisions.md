# Решения и допущения

Документ фиксирует места, где техническое задание не давало однозначного ответа: что я решила сама, почему именно так и где это закреплено в коде. В конце — что осталось за рамками сдачи.

Ссылки: [README](../README.md) — запуск и описание правил, [`Supabase/schema.sql`](../Supabase/schema.sql) — вся серверная логика.

## 1. Роли и доступ

| Вопрос | Решение | Почему |
| --- | --- | --- |
| Какая роль у нового пользователя | Всегда `executor`; роль постановщика выдаётся вручную в SQL Editor, самостоятельная регистрация отключается | Иначе любой зарегистрировавшийся мог бы сам стать постановщиком. Роль из `user_metadata` при регистрации намеренно не читается |
| Кто считается автором объекта и задачи | Всегда текущий пользователь; подставить чужой `created_by` / `author_id` нельзя | Иначе можно «повесить» задачу на коллегу |
| Какие объекты видит исполнитель | Только те, где у него есть хотя бы одна задача | Если показывать все объекты, исполнитель увидит фронт работ компании — в ТЗ этого не требовалось |
| Какие профили видит исполнитель | Себя, авторов своих задач и участников истории этих задач | Исполнителю нужны имена в карточке, но не весь штат. Постановщику доступны все — ему нужен список для назначения |
| Кто может принять задачу или вернуть на доработку | Любой постановщик, а не только автор задачи | Роль в ТЗ описана без привязки к авторству; если автор в отпуске, процесс не должен вставать |
| Видят ли постановщики задачи друг друга | Да, все постановщики видят все объекты, задачи и историю | Допущение: постановщики — доверенный круг (руководители). Если понадобится изоляция по объектам, это отдельная доработка |
| Можно ли назначить постановщика исполнителем | Нет, только профиль с ролью `executor` | Смешение ролей ломает и права, и логику переходов |
| Может ли исполнитель изменить свой профиль | Нет: `UPDATE`-политики на `profiles` нет вообще | В ТЗ не было редактирования профиля; лишние права — лишний риск. `full_name` задаётся при создании пользователя |

## 2. Задачи и статусы

| Вопрос | Решение | Почему |
| --- | --- | --- |
| Как именно меняется статус | Только серверной функцией `change_task_status`; прямого `UPDATE` для исполнителя нет | Одна точка проверки прав + блокировка строки от гонок при одновременных запросах |
| Что если клиент всё же попытается обновить статус напрямую | Триггер `tasks_before_write` отклонит запрос: он проверяет те же правила, что и функция | Защита от обхода интерфейса — прямое требование ТЗ |
| Когда можно менять исполнителя | Только в статусах «Новая» и «На доработке» и только постановщиком | После начала работы ответственный зафиксирован, иначе можно задним числом переписать, кто что делал |
| Можно ли вернуть в «Новую» | Нет: обратных переходов, кроме «На доработке → В работе», нет | Таблица переходов из ТЗ; «отмена» задачи не описана |
| «Принята» — финальный статус? | Да, выйти из него нельзя | Переоткрытие задачи в ТЗ не описано |
| Можно ли удалить задачу | Только постановщику и только в статусе «Новая» | Начатая работа не должна исчезать; удаление задачи каскадно убирает её историю |
| Можно ли удалить объект | Только если в нём нет задач (`ON DELETE RESTRICT`) | Чтобы одна кнопка не уничтожила всю историю работ по объекту |
| Что происходит при повторной смене на тот же статус | Ошибка «Задача уже находится в этом статусе», а не тихий успех | Лучше явная ошибка, чем запись-пустышка в журнале |
| Есть ли задачи без объекта | Нет, задача всегда привязана к объекту | Модель данных из ТЗ — «объекты и задачи по ним» |
| Сколько исполнителей у задачи | Один | В ТЗ — единственный исполнитель; соисполнители усложнили бы и права, и переходы |
| Меняется ли `updated_at` вручную | Нет, его выставляет триггер `tasks_updated_at` | Клиент не должен влиять на служебные поля |
| Что нельзя изменить в задаче никогда | Автора, объект, дату создания | Иначе история теряет смысл |

## 3. История и комментарии

| Вопрос | Решение | Почему |
| --- | --- | --- |
| Где хранится комментарий к переходу | В записи журнала `task_history`, а не отдельным полем задачи | Журнал неизменяем: отдельное поле пришлось бы перезаписывать, и предыдущие комментарии терялись бы |
| Когда комментарий обязателен | Только при возврате на доработку | ТЗ требует «объяснить, что доработать». При отправке на проверку и при приёмке комментарий разрешён, но не блокирует действие |
| Что видит исполнитель при доработке | Баннер в карточке задачи с последним комментарием к доработке + полную историю переходов | Комментарий должен попадаться на глаза, а не прятаться в журнале |
| Кто пишет в журнал | Только триггер `log_task_status_change`; у клиента нет прав `insert/update/delete` на таблицу | Подделать запись «я всё сделал» или переписать историю нельзя |
| Можно ли удалить отдельную запись журнала | Нет; записи уходят только каскадом вместе с самой задачей | Аудит должен быть непрерывным |
| Как комментарий попадает из функции в триггер | Через локальную настройку транзакции `app.status_comment`, которую выставляет `change_task_status` | У клиента нет способа выставить её самостоятельно: произвольный SQL через API не выполняется |
| Пишется ли запись при создании задачи | Нет: первая запись появляется при первом переходе | «Новая» — это стартовое состояние, а не переход |
| Виден ли журнал исполнителю | Да, но только по своим задачам | Ему нужен контекст: что просили исправить и когда |

## 4. Данные и инфраструктура

| Вопрос | Решение | Почему |
| --- | --- | --- |
| Одна миграция или много | Один идемпотентный файл `Supabase/schema.sql`: его можно применять повторно и на чистую, и на рабочую базу | Удобно для проверки задания: один шаг развёртывания, без `supabase` CLI и локального Docker |
| Почему в схеме есть `GRANT` | RLS-политики сами по себе прав не выдают: без `GRANT` роль `authenticated` получает «permission denied for table» | Это первая же ошибка при развёртывании на новом проекте, поэтому права выданы явно и минимально |
| Нужен ли `anon` | Нет: у анонимной роли отозваны все права на таблицы | Без входа в систему данных не видно вообще |
| Язык интерфейса | Русский; коды статусов (`new`, `in_progress`, …) — латиницей в базе, подписи — в интерфейсе | Коды стабильны для API, подписи можно менять без миграции |
| Ошибки базы | Тексты исключений в PostgreSQL написаны по-русски и показываются пользователю как есть | Одна формулировка правила и в коде, и на экране — меньше расхождений |
| Как проверялся сценарий | Вручную по шагам из README, плюс запросы от имени каждого пользователя к базе (что видно, что нельзя) | Автотестов нет — см. следующий раздел |

## 5. Что не сделано

**Сознательно вне рамок** (в ТЗ не было, добавило бы объём без пользы для демонстрации):

- сроки (дедлайны), приоритеты, теги задач;
- вложения и фотографии;
- обсуждение задачи вне смены статуса (переписка в карточке);
- уведомления по почте и обновление списков в реальном времени;
- полнотекстовый поиск, фильтры по датам, пагинация — при демо-объёмах это преждевременно;
- управление ролями из интерфейса (сейчас — один запрос в SQL Editor);
- самостоятельная регистрация, приглашения и сброс пароля письмом — настраивается средствами Supabase Auth;
- мультиязычность;
- аудит изменений, кроме статусов (кто переименовал задачу — не фиксируется);
- отдельное мобильное приложение (интерфейс адаптирован под узкий экран).

**Не успела / можно добавить в первую очередь:**

- автотесты и CI: сценарий «создал → взял в работу → вернул на доработку → принял» сейчас проверяется вручную (шаги в README). Первым делом автоматизировала бы именно его;
- скелетон-загрузка и оптимизация размеров бандла (сборка предупреждает, что чанк больше 500 КБ);
- ограничение частоты запросов и капча на форму входа.

## 6. Что учесть при развитии

1. **Роли назначаются SQL-запросом.** Для небольшой команды это нормально, но при росте нужен экран администрирования и журнал изменений ролей.
2. **Все постановщики видят всё.** Если появится несколько независимых направлений, понадобится изоляция объектов по подразделениям — это изменение политик и модели данных.
3. **Один исполнитель на задачу.** Соисполнители потребуют таблицы-связки и переработки переходов статусов.
4. **Правила живут в триггерах.** Любая правка `schema.sql` требует прогона сценария из README: сломать защиту легко, и внешне это никак не проявится.
5. **`service_role`-ключ нельзя использовать во фронтенде** — он обходит все политики. В браузер попадает только `anon`-ключ.
6. **Сброс пароля и приглашения** — настраиваются в Supabase Auth; в коде для этого ничего менять не нужно.

## 7. Итог

Все проверки прав продублированы на двух уровнях: интерфейс подсказывает только доступные действия, а база данных независимо проверяет те же правила. Поэтому даже прямой запрос к API в обход интерфейса не даёт исполнителю лишних возможностей — это и было главной целью задания.
